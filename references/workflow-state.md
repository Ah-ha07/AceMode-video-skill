# 编排状态与确认语义

编排不是让三个 Skill 同时运行，而是把上一步的证据和用户决定，作为下一步唯一可信的输入。`project.json` 是跨轮次的状态凭证。

## 单条故事状态

| 状态 | 含义 | 下一步允许动作 |
| --- | --- | --- |
| `SELECTED` | 已绑定雷达快照中的固定序号 | 写稿 |
| `SCRIPT_DRAFT` | 稿件与事实账本已注册，未确认 | 修改或确认稿件 |
| `SCRIPT_APPROVED` | 用户确认了当前稿件哈希 | 重查来源、制作视频方案与预览 |
| `PREVIEW_READY` | 当前素材、声音、场景和审片包已登记 | 用户审片 |
| `RENDER_APPROVED` | 用户在最新预览之后单独同意完整渲染 | 完整渲染与最终 QA |
| `COMPLETED_INTERNAL` | 技术 QA 已通过，但 publication 仍可能有素材替换项 | 团队审片或清权后重新做公开交付 |
| `COMPLETED` | publication 与技术 QA 均通过，公开成片路径已登记 | 交付或从任一上游阶段另起修订 |

## 两道不能合并的确认门

稿件确认回答的是内容能不能进入制作。用户在看到完整稿件后说可以、定稿、按这个做，可登记 `SCRIPT_APPROVED`。含糊的继续看看、不用改这个点、先做个样片不等于稿件定稿。

成片确认回答的是是否允许做耗时的完整渲染。必须先给用户最新的封面帧、带声音的前三秒预览、代表性关键帧板、实测时长和版权阻塞项；用户在看到这些之后明确同意完整渲染，才登记 `RENDER_APPROVED`。稿件确认不能替代成片确认。

状态机要求当前哈希的展示审计事件：稿件展示用 `present-script`，审片展示用 `present-preview`。确认命令只在对应事件存在时生效。receipt 写任务/对话中的可追溯轮次标识。这是执行者对已展示事实的可审计声明，不是宿主签名，技术上不能证明用户真的看过；它不能替代语义判断，但能阻止无展示事件的直接自批。若宿主提供不可伪造的 message/turn ID，应优先把该 ID 用作 receipt。

## 失效规则

- 重新注册稿件：清除稿件确认、来源复核、预览、成片确认和完成状态。
- 生产前复核发现事实、数字、能力、发布时间或边界有实质变化：退回 `SCRIPT_DRAFT`，修稿并重新确认。
- 来源复核未发现实质变化：保留稿件确认，允许制作预览。
- 预览后更换口播文字、voice ID、字幕时间、关键素材、版权状态、导演方向、场景结构、转场、画幅、封面或开场：重新生成并登记预览，再次取得成片确认。
- 只修复不会改变成片观感或含义的纯技术问题时，也要保证状态脚本登记的所有文件哈希仍一致；不一致就重新登记。

状态脚本是门禁，不是事实判断器。是否属于实质变化需要结合稿件主张、事实账本和用户看到的版本判断，并逐项写进 `source-recheck.json`。每次续接先运行 `status`；`integrity.ok` 不为 true 时不得推进。
